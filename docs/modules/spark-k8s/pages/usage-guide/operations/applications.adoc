= Spark applications
:description: The lifecycle of Apache Spark applications submitted as SparkApplication resources, covering resubmission and their Prometheus metrics.

Spark applications are submitted to the Spark Operator as SparkApplication resources.
These resources are used to define the configuration of the Spark job, including the image to use, the main application file, and the number of executors to start.

Upon creation, the application's status set to `Unknown`.
As the operator creates the necessary resources, the status of the application transitions through different phases that reflect the phase of the driver Pod. A successful application eventually reaches the `Succeeded` phase.

NOTE: The operator never reconciles an application once it has been created.
To resubmit an application, a new SparkApplication resource must be created.

== Clean-up of finished applications

While an application runs, the SparkApplication owns everything the operator created for it: the spark-submit Job, the driver Pod, the ServiceAccount, the RoleBinding and the ConfigMaps.
Once the driver Pod finished, the operator hands the driver Pod and these objects over to the Job.
Kubernetes deletes the Job after it finished and its time to live expired, and everything that was handed over to it is deleted together with it.
The executors are owned by the driver Pod and are deleted with it, if Spark has not already deleted them.

The time to live is set with `spec.cleanup`, separately for a driver Pod that succeeded and one that failed:

* `afterSucceeded`: the time to live if the driver Pod succeeded. The default is `10m`.
* `afterFailed`: the time to live if the driver Pod failed. The default is `10m`.

Each accepts:

* a duration such as `30m`: the objects are kept for this long after the Job finished.
* `0s`: the objects are deleted as soon as the Job finished.
* `never`: the objects are kept until the SparkApplication is deleted.

[source,yaml]
----
apiVersion: spark.stackable.tech/v1alpha1
kind: SparkApplication
metadata:
  name: example
spec:
  cleanup:
    afterSucceeded: 5m
    afterFailed: 1d
  ...
----

Deleting the SparkApplication deletes all of these objects at any time.
The phase of the application is kept in the status of the SparkApplication after the objects were deleted.

The operator creates the Job with the longer of the two times to live and sets the one matching the phase of the driver Pod when the driver finished.
Whether an application counts as failed depends only on the phase of the driver Pod, not on the status of the Job.
If no driver Pod finished, for example because spark-submit failed before creating one, the Job keeps the longer time to live.

NOTE: The times to live are fixed when the operator creates the Job.
Changing `cleanup` of an application that was already submitted has no effect.

NOTE: With `spark.kubernetes.submission.waitAppCompletion: "false"`, the Job finishes right after the submission and its time to live starts then.
If the Job is already deleted when the driver finishes, the operator deletes the driver Pod and the other objects right away.

NOTE: If `spark.kubernetes.driver.pod.name` is set, the operator deletes the driver Pod as soon as it finished, so that the next submission or retry can create a driver Pod with the same name.
The other objects are still kept for the time to live from `cleanup`.

== Monitoring

[NOTE]
====
Starting with version 25.7, the built-in Prometheus servlet is enabled.
The JMX exporter is available but not used for applications. It has never been used automatically for applications and now it is deprecated.
====

Application driver pods expose Prometheus metrics at the following endpoints:

* `/metrics/prometheus` for driver instances
* `/metrics/executors/prometheus` for executor instances.

These endpoints are available on the same port as the Spark UI, which is 4040 by default.
